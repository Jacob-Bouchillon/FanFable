# FanFable — System Report

**Date:** 2026-10-28
**Scope:** current architecture, every subsystem, the evidence rules, and the model findings measured this session.
**Status of the tree:** `main` at `2bb90d1`, clean, synced with origin. The findings below were produced after that commit and are not yet committed.

---

## 1. What the system is

FanFable is a local-first fanfiction engine. A book is imported, read once, and turned into a **bank of proven claims**; the bank, not the raw text, is what the planner and writer are allowed to treat as canon.

The product thesis is narrow and deliberate:

- **Canon is evidence, not vibes.** A tie between two people is banked only when a verbatim quote from the source proves it. Everything else is parked and visible to a human.
- **The model proposes; the system decides.** No model, local or cloud, can set a keeper status. Models produce candidates, the deterministic guard decides.
- **Local by default.** A user's book never leaves the machine unless they explicitly configure a cloud provider. Cloud support exists for development.

Those three rules constrain every design decision below.

### Fixed constraints

| Constraint | Value | Consequence |
|---|---|---|
| Ship VRAM ceiling | 8GB | The reader must fit with headroom; 6.1GB is the current high-water mark |
| Ship concurrency | 1 | A single model slot on user hardware |
| Dev box | 16GB VRAM, 30GB RAM | Two parallel decode slots, measured |
| New runtime dependencies | none | Node built-ins plus SQLite only |
| Universality | no book-specific terms in `fanfable/src` or `testing/tests` | Book knowledge lives in `data/`, fixtures and `testing/trials/` |

     ├── lore.ts / lorebook.ts        canon: import, extraction, bank

## 3. The canon pipeline

### 3.1 Import and chunking

`importer.ts` turns PDF/EPUB/DOCX into plain text with page markers, so citations can point at a page. `text.ts` chunks the text into passages, each with a `seq` and a locator.

Two chunkers exist. The **old** one produced 1,448 passages for the test book by duplicating content; the **rebuilt** one produces 738. The live bank (`testing/trials/halfbook-run/plagueis-half.db`) still uses the old chunker. Every model comparison this session used the rebuilt chunker for exactly this reason: it is the one we intend to ship.

### 3.2 Windows and selection

Extraction reads **windows of 8 consecutive passages** (~1,500 words). The book is 93 windows under the rebuilt chunker.

When a run is budgeted (`--max-windows n`), windows are chosen by a priority score — the logs read `bridge×50, names×10, relations×10` — so a small run samples the densest parts of the book, not a representative slice. That matters when interpreting every 10-window result in this report: **the ten windows are the ten richest, so per-window rates from them overestimate the whole book.**

### 3.3 The extraction call

Extraction is split into three narrow calls per window rather than one large one:

1. entities + facts,
2. relations between known names,
3. events.

The reason is mechanical: a 7–9B model handed four schemas at once answers the first and rushes the rest, and one truncated answer loses the whole window. Three calls each produce a complete, checkable answer, and a failed section costs only that section.

The relations schema asks for `from`, `to`, `kind`, `description`, `chunk_index`, `evidence`, and `modality`. In the **default** prompt, `kind` is "one short phrase, such as 'sibling of'" — open-ended. In **strict** mode (`FANFABLE_REL_STRICT=1`), kinds are closed to 36 labels and the model must produce one contiguous sentence naming both endpoints.

That difference turns out to matter a great deal for NuExtract, and not at all for qwen. See §8.

### 3.4 Quote verification

Every claimed quote is checked against the actual passage text, locally and without a model. The counters reported at the end of a run are:

| Counter | Meaning |
|---|---|
| verified | quote appears verbatim in the cited passage |
| repointed | quote found in a different passage, reference corrected |
| dropped | quote not found at all |
| unresolved | relation named an entity that does not exist in the bank |
| unrelated | quote does not concern the claimed endpoints |
| moment | a one-off event masquerading as a lasting tie |
| redundant | duplicate of a row already banked |
| unsupported | tie word absent from the quote |
| hinted | a co-occurrence hint kept for later |
| retried | strict-mode second attempt at a both-name sentence |

This stage is deterministic. It is the reason a model cannot lie its way into the bank: the quote either exists in the text or it does not.

### 3.5 The promotion guard

`canPromote()` is the single gate. A parked tie becomes a keeper only when **all** of these hold:

1. **Closed relationship-grade kind** — not coverage-only, not a moment, not open vocabulary.
2. **No PARK ruling** on the pair or its inverse class — a human ruling binds the pair regardless of new quotes. New evidence becomes a pending note, never a status change.
3. **Quote verbatim in its cited passage.**
4. **Both endpoints named in that quote** (name or alias, exact match).
5. **Tie word present** and **direction not reversed**.

The fourth and fifth conditions are the ones that cap the whole system. The book must, in one sentence, name both people and state the relationship. Most prose does not.

An important precision note: the A/B metric used in this report (`provable` = closed kind + both names + tie word) is **looser than `canPromote`**, which also requires a verbatim quote and a non-reversed direction. Running `canPromoteRelation()` over the same rows gives the true count:

| Bank | Metric "provable" | Guard-eligible |
|---|---:|---:|
| qwen3.5 Q4, run 1/2/3 | 2 / 1 / 2 | **1 / 1 / 1** |
| qwen3.5 Q3, run 1/2 | 0 / 1 | 0 / 1 |
| NuExtract3 strict | 2 | **2** |
| NuExtract3 default | 0 | 0 |
| NuExtract 1.5 | 0 | 0 |

The missing rows fail on a spliced quote, not on the tie. So "2 provable" should be read as "2 candidates that clear the named checks", and the system's actual yield at this sample is one keeper per ten priority windows for qwen3.5 — and two for NuExtract3 strict in its single run.

### 8.1.1 Guard audit on the ten-window banks

`testing/trials/model-ab/guard-audit.ts` re-evaluates every relation row against each promotion predicate independently, including the ones the guard's short-circuit never reaches, and compares the recomputed first failure with the reason persisted in `canon_tie_note`.

**The persisted reason is not the guard's reason.** Ten of twelve parked rows in the qwen bank and 82 of 99 in the NuExtract bank disagree with `canPromoteRelation()`. Rows stored as `unsupported` are in fact `endpoint-unnamed`, `quote-not-verbatim` or `open-vocab`. The note trail is written by a different code path and cannot be used as a measurement of guard behaviour without this recomputation.

**Per-predicate failure counts** (a row may appear in several):

| Predicate | qwen3.5 (22 rows) | NuExtract3 strict (99 rows) |
|---|---:|---:|
| endpoint-unnamed | 16 | 89 |
| kind-open-vocab | 11 | 4 |
| kind-not-relationship-grade | 11 | 4 |
| tie-word-absent | 9 | 88 |
| quote-not-verbatim | 3 | 7 |
| direction-reverse (first failure only) | 0 | 0 |
| **fails exactly one predicate** | **3** | **11** |

**2×2 diagnostic — label validity against evidence adequacy:**

| Bank | label valid + evidence valid | label valid + evidence bad | label bad + evidence ok | both bad |
|---|---:|---:|---:|---:|
| qwen3.5 | 1 | 10 | 3 | 8 |
| NuExtract3 strict | 2 | 93 | 1 | 3 |

Definitions, stated precisely:

- **label valid** — the kind is closed, relationship-grade, and not a moment kind.
- **evidence valid** — the quote is verbatim in its cited passage (after the guard's own normalisation: lowercase, punctuation except apostrophes replaced by spaces), both endpoints are named exactly (name or alias), and a tie word for the kind is present.
- **not tested by either** — direction (reported separately), and whether the relationship is semantically correct. A row can be "evidence valid" and still be wrong. Adjudication, not the vector, decides that.

The 2×2 separates the two models' problems: qwen's failure is split between label and evidence, NuExtract's is almost entirely evidence — 93 of 99 rows carry a legal label over a quote that does not establish the tie.

Caveat: ten deliberately dense windows. These distributions are not book-wide estimates.

### 8.1.2 Why endpoint naming fails

`testing/trials/model-ab/evidence-split.ts` classifies every row that failed endpoint naming, using only the passage and the bank's names:

| Bucket | Meaning |
|---|---|
| alias | the quote names the endpoint by a surface the bank does not hold (surname, title, partial) |
| adjacent | the missing endpoint is in the sentence next to the quote, with the tie — a two-sentence proof would work |
| sameSentence | a sentence in the passage names both endpoints; the model quoted a different one |
| splitAcrossSentences | both endpoints are in the passage but never in the same sentence |
| absent | the endpoint is not in the passage at all |

| Bank | both named | alias | adjacent | same sentence | split | absent |
|---|---:|---:|---:|---:|---:|---:|
| qwen3.5 default (22) | 6 | 2 | 4 | 3 | 5 | 2 |
| qwen3.5 strict (23) | 5 | 2 | 5 | 1 | 7 | 3 |
| NuExtract3 default (83) | 12 | 14 | 9 | 6 | 22 | 20 |
| NuExtract3 strict (99) | 10 | 16 | 4 | 8 | 34 | 27 |

Two conclusions:

- **The structural bucket is real and sizeable.** For qwen, 5–7 of 22–23 candidates (23–30%) have both names in the passage but never in one sentence. No prompt fixes that; it is the measured cost of the one-sentence proof rule, before any judgement about whether those pairs are true ties.
- **Wrong-quote selection is small** (1–8 rows). The mechanism I expected to dominate does not.
- NuExtract's largest bucket is *absent from the cited passage* (20–27). Checked against the whole book rather than the cited chunk, most of those pairs are not invented: of its 99 rows, 49 name both parties in a sentence elsewhere in the book, 9 in another sentence of the cited passage, 10 in the quote itself, and **31 never co-occur in any sentence at all**. For qwen the same breakdown is 7 / 8 / 6 / **1**.

Caveat: "split" means the tie cannot be proved by one sentence. It does not mean the relationship is true.

### 3.6 Tiers

| Tier | Meaning | Visible in answers? |
|---|---|---|
| `accepted` | proven by the guard | yes |
| `user_confirmed` | a human ruled on it | yes |
| `provisional` | plausible, unproven — including co-occurrence | **no** |
| `needs_review` | parked with a reason | no |

`confirmed_by_user` is preserved through status changes, so a later extraction run cannot quietly overturn a human decision.

The ten keepers that could not be re-proved from the text are **quarantined, not deleted**: they stay provisional with their confirmations intact.

### 3.7 Enrichment and the loopback

A single pass never captures a book. `lore-diagnostics.ts` finds thin entities — a character with hundreds of mentions and one tie — and re-reads the passages about them. In a 10-window run this is two extra calls at the end.

The chain handoff (`chain-handoff.ts`) is the product-side half of a shared format: windows in read order, thin names and where they appear, banked pairs with quote, place and review flag. It never changes what is banked; it only orders what `enrich` re-reads.

## 4. Retrieval and answering

`retrieval.ts` assembles one context from four sources: passages (FTS5), the knowledge graph, story memory, and character knowledge. `graph.ts` supplies the graph, with:

- **PPR** (personalised PageRank) to spread from query seeds along every edge, including mention edges;
- a **recognition filter** (`recognition.ts`) that drops dense seeds lacking lexical backing — a query for "sibling" should not fire on a "brother" triple whose passage says nothing about siblings;
- **passage trails**: for each top passage, the labelled chain of nodes that led to it, capped at six steps.

`lore-ask.ts` answers canon questions. It is the only path allowed to state a relationship, and it has an answer guard: an asserted tie must exist in the bank, citations are verified against the passage, and `FANFABLE_NO_GUARD=1` exists only for experiments.

The guard was added because the earlier pipeline produced answer-level overclaims — correct-sounding relationships that were never banked. The bank is the exam: if a tie is not in it, the answer cannot assert it.

## 5. The story pipeline

### Planner
Owns premise, AU divergence point, structure, chapter outlines and arcs. It asks before treating anything as established and never discards approved material.

Known defect from the product loop: `selectCanonEvents` picks canon events by word overlap, so the planner can anchor to the wrong event. Outlines also cite nothing, which makes an anchor error invisible until the prose contradicts it.

### Writer
Writes chapters sequentially from the approved plan, using canon passages, story memory, character states and instructions. It can stop mid-draft and request more information through a structured block; the controller resolves the request and feeds it back, de-duplicated and capped so a model cannot loop.

### Continuity
Checks prose against outline, previous chapters, canon and AU state. It reports with evidence, never rewrites, never rejects an intentional divergence. The keeper-denial check detects a chapter that denies a banked tie; model findings without chapter evidence are dropped; notes are persisted and filtered at display. Default `minSeverity` is `warning`, and notes are visible with `issues --all`.

### Memory and state conflicts
`memory.ts` owns the AU story: outline, chapters, timeline, characters, knowledge. `state-conflicts.ts` records contradictions between a new chapter and established state — it keeps both and reports provenance. A continuity issue is a problem inside the prose; a state conflict is a problem between the prose and the record.

## 6. Model access

`llm.ts` hides three providers behind one interface:

| Provider | Endpoint |
|---|---|
| `ollama` | `{base}/api/chat` (default) |
| `llamacpp` | `{base}/v1/chat/completions` |
| `openai` | `{base}/v1/chat/completions` (any compatible gateway) |

JSON mode maps to Ollama's `format: 'json'` and to `response_format: {type:'json_object'}` elsewhere. `seed` is passed when configured. API keys are withheld from loopback addresses so a local server never receives a cloud key by accident.

Provider configuration is global (`~/.config/fanfable/config.json`) with per-project overrides. The `openai` path appends `/v1/chat/completions`, so an OpenRouter base URL must be `https://openrouter.ai/api`, not `.../api/v1`.

## 7. Verification and evidence discipline

The system's credibility rests on artifacts, not assertions:

- **`lore integrity`** — every keeper's quote must be verbatim in a cited chunk. Exits non-zero if not.
- **`lore evaluate`** — judges each banked tie with understanding; failures park as notes.
- **`rule-checker.ts`** — ~20 deterministic SQL and string rules that flag contested rows with machine-readable reasons. No model, no VRAM.
- **`lore rulings export/replay`** — human rulings are portable across rebuilds.
- **Test suite** — `testing/tests/`, 474 passing at the last full run before this session, `tsc` clean.

The distinction that keeps this honest: a passing test establishes that a mechanism behaves as specified. It does not establish that the mechanism is effective. The A/B numbers below are the effectiveness evidence; the tests are the regression evidence.

## 8. Model findings (this session)

All runs: same book, same 10 priority windows, same seed, same prompt, `think:false`, concurrency 3, fresh database each time. `provable` = closed kind + both names in quote + tie word.

### 8.1 Reader comparison

| Model | Relations | Closed | Both named | Tie word | Provable | Time |
|---|---:|---:|---:|---:|---:|---:|
| qwen2.5:7b Q4 (incumbent) | 28 | 14 | 1 | 16 | 0 | 3m50 |
| qwen2.5:7b Q8 | 15 | 2 | 3 | 12 | 0 | 6m06 |
| qwen3:8b | 15 | 8 | 3 | 9 | 0 | 6m41 |
| llama3.1:8b | 15 | 10 | 1 | 5 | 0 | 8m13 |
| **qwen3.5:9b Q4**, run 1 | 22 | 11 | 6 | 13 | **2** | 5m31 |
| **qwen3.5:9b Q4**, run 2 | 26 | 17 | 5 | 13 | **1** | 5m59 |
| **qwen3.5:9b Q4**, run 3 | 37 | 23 | 10 | 16 | **2** | 5m41 |
| qwen3.5:9b Q3_K_M, run 1 | 11 | 5 | 1 | 7 | 0 | 4m07 |
| qwen3.5:9b Q3_K_M, run 2 | 9 | 5 | 4 | 5 | 1 | 4m17 |
| NuExtract3, default prompt | 83 | 11 | 12 | 43 | 0 | 7m12 |
| NuExtract3, strict prompt | 99 | 95 | 10 | 11 | 2 | 5m17 |
| NuExtract 1.5, default prompt | 8 | 0 | 1 | 5 | 0 | 6m58 |

**What this establishes**

- qwen3.5:9b is the only model that produced provable ties, and it did so in all three runs (2/1/2). It also produced four to five times more both-named quotes than any other chat model.
- The same two pairs recur every run. The gain is reliable quoting discipline, not broad new discovery.
- Four models produce zero provable ties. That is a real capability gap, not noise: the metric is deterministic once the model's output is fixed.

**What it does not establish**

- That qwen3.5 wins across the other 83 windows. The ten windows are the richest.
- That qwen3.5's advantage survives a different book.
- That the ceiling is a property of the prose in general. It is a property of *these windows of this book* under *this standard*.

### 8.2 Quantization

Q4_K_M (5.68GB weights, 6.1GB loaded) is the floor. Q3_K_M (4.67GB weights, 4.5GB loaded at 4k context) halves relations, halves both-named evidence, and produced one unverified keeper that `lore integrity` caught. The 1.2GB saved is not worth it. If an 8GB machine is marginal, the lever is `num_ctx`, not bits.

The default Ollama tag for qwen3.5:9b is already Q4_K_M; there is no full-precision option that fits the ship target (bf16 is 17.9GB, Q8 is 9.5GB).

### 8.3 NuExtract, and the interface question

NuExtract is a **span-copier**: text + JSON template in, filled template out. It has no chat behaviour to speak of.

- Under the default prompt (which invites invented kinds) it produced 83 relations, 12 both-named quotes, 43 tie-word quotes, and **0 provable** — because only 11 rows used a closed kind.
- Under strict mode it obeyed the closed list almost perfectly (95 of 99 rows) and reached **2 provable** — exactly qwen's number, inside four times the rows, with 96 of those rows naming entities it never resolved.
- Its 48 strict quote retries **all failed**: asked for one contiguous sentence naming both endpoints, it could not produce one on any of the 48 attempts.

That last number is the strongest evidence in the session: the constraint is the text, not the model. A model that copies spans for a living cannot manufacture a sentence that does not exist.

Where it remains plausible: **targeted pair probing**, where the pair is given and the template can carry our closed kind list. Open-ended extraction is where it fails; constrained extraction is what it was trained for. That hypothesis is untested.

### 8.4 Name finding

Eight passages mentioning thin entities, three models:

| Model | Names | Verbatim | With sentence | Already on roster | New | Fragments | Time |
|---|---:|---:|---:|---:|---:|---:|---:|
| NuExtract3 | 93 | 93 | 93 | 81 | 12 | 5 | 18s |
| NuExtract 1.5 | 41 | 41 | 37 | 36 | 5 | 1 | 14s |
| qwen3.5 | 78 | 76 | 33 | 72 | 4 | 8 | 65s |

The capitalization roster already contains ~87% of what the models find, and the "new" names are mostly artifacts, titles, categories and possessive phrases. Name **finding** is not the bottleneck; name **resolution** is — and NuExtract's characteristic failure is splitting one person into several entities.

### 8.5 Hardware behaviour

- Ollama runs **two parallel decode slots** on this card: 3 concurrent requests took 3.3s, 6 concurrent took 7.0s (two batches of two), sequential 3 took 6.8s.
- qwen3.5:9b Q4 loads at **6.1GB** with a 16k context, 100% GPU-resident.
- Full-book cost at concurrency 3: ~55 minutes for qwen3.5, ~50 for NuExtract3, ~36 for qwen2.5:7b.
- At ship concurrency 1, multiply by roughly three.

## 10. Open problems

1. **The proof standard is tight and the prose is loose.** Across 10 windows, 22–37 candidate relations yield 2 provable ties. Extrapolating naively to the book gives tens, not hundreds. Every model tested hits the same wall.
2. **Anchoring errors in the planner.** Word-overlap selection can pick the wrong canon event; outlines cite nothing, so the error is silent.
3. **The rebuilt bank is thinner.** 738 chunks means fewer passages per window and fewer candidates than the 1,448-chunk bank the live numbers come from. It has not been promoted or replayed yet.
4. **Cross-window ties are invisible.** Extraction reads 8 passages at a time and the guard requires one sentence. Relationships established across chapters cannot be banked by the current design; the 3,071 co-occurring pairs represent that gap.
5. **Model variance.** 22 versus 37 relations on identical input. Single runs cannot rank models; the medians above are from three runs for qwen3.5 and one for the rest.
6. **Ship headroom is unmeasured.** 6.1GB on a 16GB card is not the same as 6.1GB on an 8GB card with a compositor; partial CPU offload would be a silent 10× slowdown.

## 13. Verdict in one paragraph

The system does what it claims: it banks only what a verbatim quote proves, it keeps humans in control of the rest, and it can explain every keeper. Its weakness is not the guard but the input — real prose rarely states a lasting relationship in one sentence naming both people, so the bank grows slowly no matter which model reads. qwen3.5:9b is the best reader measured (one guard-eligible keeper per ten priority windows, repeatable, 6.1GB, ~55 min for the book); Q4 is the quantization floor; NuExtract is a recall machine whose kinds and entities need a judge, and whose strict-mode output produced two guard-eligible keepers in its single run — a result the full-book comparison will test. The next honest test is bank-level, not window-level: run both models over the whole book and adjudicate what one found that the other missed.
